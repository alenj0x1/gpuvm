Every improvement is tested before it's adopted: a hypothesis, a baseline configuration, a candidate configuration and repeated measurements.

## Workflow

<Steps>

1. **Open a lab** with a title and a hypothesis. Optionally give the baseline and candidate a profile and an override.

   ```powershell
   ./gpuvm.ps1 lab-new -Title 'More threads' -Hypothesis '10 threads raise FPS without hurting the host' `
     -BaselineProfile max-performance -CandidateProfile max-performance `
     -CandidateOverride @{ vm = @{ cpu = @{ count = 10 } } }
   ```

2. **Measure the baseline** several times. Before each measurement you can run `guest/collect-info.ps1` inside the VM: it saves the state of the GPU, the CPU and the power plan, plus a `dxdiag`.

   ```powershell
   ./gpuvm.ps1 lab-add -Lab 002 -Variant baseline -Metric 'Time Spy GPU' -Value 10210 -Unit pts
   ```

3. **Apply the candidate and measure again** with `-Variant candidate`. Use `-LowerIsBetter` for metrics such as latency, and `-Notes` for observations.

   ```powershell
   ./gpuvm.ps1 lab-add -Lab 002 -Variant candidate -Metric 'Time Spy GPU' -Value 10480 -Unit pts
   ```

4. **Compare**: averages per metric and the difference in %.

   ```powershell
   ./gpuvm.ps1 lab -Lab 002
   ```

5. **Close it** as `adopted`, `rejected` or `inconclusive` with a conclusion. When a lab is adopted, carry the candidate configuration to the matching profile in `profiles/`.

   ```powershell
   ./gpuvm.ps1 lab-close -Lab 002 -Status adopted -Conclusion '+2.6 % GPU; moved to max-performance'
   ```

</Steps>

`-Lab` accepts the lab's number (the start of its folder name). `./gpuvm.ps1 lab` without `-Lab` lists all labs with their status and number of results.

## Where labs live

Each lab is a folder `labs/NNN-name/` with `lab.json` (hypothesis, variants, results and conclusion) and `notes.md` (procedure and observations). From the repository they are in `labs/`; with the installed app they go to `%ProgramData%\GpuVM\labs`. The `GPUVM_LABS_ROOT` environment variable points them somewhere else.

### What the labs found so far

- **002:** in the first real test (Windows 10 22H2 VM) Sunshine installed, paired on its own and detected NVENC, but Moonlight showed black: Sunshine was capturing the Hyper-V display instead of the virtual one. The fix (set `output_name` to the virtual display and `dd_configuration_option = ensure_only_display`) is now done automatically on every **start and open**. Still pending: Sunshine reports "Display device configuration API is temporarily unavailable" and doesn't change the resolution.
- **003:** VB-CABLE Pack45 was chosen over the VDD project's Virtual Audio Driver (beta, needs test signing), Scream (needs Secure Boot off) and Steam Streaming Speakers (requires installing Steam, no pinned version). Replaced by GpuVM's own USB speaker after lab 011 showed VB-CABLE is silent to Sunshine inside a VM; see [Audio](/gpuvm/docs/streaming/#audio).
- **004:** measured with the end-to-end meter in `tools/latency` (1080p, 60 FPS, 40 presses on the `win10` VM). Median **38.9 ms with V-Sync** vs **33.8 ms without**: about 5 ms less, under one frame, and the p95 halves (231.5 → 122 ms). Part of the p95 and the missed samples come from the meter itself. With V-Sync, Moonlight's overlay showed 57.12 FPS received, 1 ms network and 0.32 ms decode. 120 and 144 FPS aren't measured reliably yet: the stream stayed black because the refresh rate changed while the previous Sunshine session was still open; the tools now close it between variants. Still open.
- **006:** rewritten. The host reports the root scheduler (`Hypervisor scheduler type is 0x4`), and Microsoft documents that caps, weights and reserves only apply with the classic or core scheduler, so 30 % vs 100 % reserve couldn't show a difference. It now compares 8 vs 6 virtual processors. No results yet.
- **007:** rewritten. The first candidate (preset 1, `quarter_res`, latency over power) equalled Sunshine's defaults. The new candidate turns off two-pass, the VBV increase and split encode. No results yet.
- **008 (adopted):** opening without changing resolution or FPS went from 22–27 s to the first frame (26.8 s measured) to **2.1 s**. Changing the mode still costs 10–15 s (13.3 s for 120 FPS after 60). With `ensure_only_display`, Sunshine's log showed "Encoder reenumeration is required" on every session. `connect` now sets `dd_configuration_option = disabled` when GpuVM already turned the Hyper-V display off. See [Streaming](/gpuvm/docs/streaming/#sunshine).
- **009 (adopted):** A game in exclusive fullscreen at 800×600 was black with `ddx` (Sunshine got no new frames and re-sent the last one) and visible with `wgc`. Adopted as a per-VM option, off by default (**Options → Capture**; Fast, `wgc`, became the default after lab 023): `wgc` doesn't show Windows' administrator prompts (secure desktop). No security change: in `wgc` Sunshine runs as the signed-in user (elevated) instead of SYSTEM. See [Capture modes](/gpuvm/docs/streaming/#capture-modes).
- **010 (adopted):** with the rules, none of the host's TCP ports (4 before) and none of the router's checks (3 before) were reachable from the VM, by IPv4 or IPv6; internet, DNS, DHCP and Sunshine kept working and connect time didn't change (0.35 ms). On by default (**Options → Network**).
- **011 (rejected):** both VB-CABLE outputs reach Sunshine as digital silence inside the VM while Windows' meter shows sound; Moonlight received nothing. The sound that seemed to work came from Steam Streaming Speakers (0.265 in Moonlight).
- **012 (adopted):** GpuVM's speaker, **Speakers (GpuVM Audio)**, was captured at the same level as Windows' meter (0.356) and reached Moonlight at 0.351, louder than Steam's 0.265, with no transfer errors. usbip-win2's drivers are signed by Microsoft and it adds no certificate. See [Audio](/gpuvm/docs/streaming/#audio).
- **018 (adopted):** the pipe costs under 1 ms to connect and queries take the same time; the client and server checks held. The bridge runs with the user's elevated token, not as SYSTEM (as SYSTEM the saved guest passwords can't be decrypted), GpuVM carries its own PowerShell 7, paths are checked as the unelevated user and deletions ask for UAC. See [Architecture](/gpuvm/docs/architecture/#bridge-between-the-app-and-powershell).
- **019 (adopted):** a warm open spent about 22 of its ~25 s repeating guest work through separate PowerShell Direct calls, and the job ended 3–17 s before the first frame. With one session, work once per boot, readiness from the heartbeat and waiting for the first frame: warm 7–10 s including the first frame, cold about 55 s (was 77–90 s). Still open: Sunshine's own startup.
- **020 (adopted with 022):** about 16.6 ms median from input on the host to Moonlight's picture at 120 FPS or more (5.6 ms locally, so the stream adds about 11 ms); 60 FPS adds a host frame; codec and window mode don't change the median. Led to the per-machine uses and the V-Sync, frame pacing and mouse settings.
- **021 (partly adopted):** frame pacing only helps at 60 FPS, the **Movies and video** use; at 120 FPS and above it adds stutters. 165 FPS was the smoothest.
- **022 (adopted):** at the monitor's rate (180 Hz) stutters fell to 0.4–0.8 % (about 1 % before) and V-Sync added no latency. `fps = 0` follows the monitor; new VMs use it with V-Sync on.
- **023 (adopted):** desktop duplication restarts silently at session start; WGC showed the picture in about 2.6 s in 9 of 10 reconnects. WGC became the default capture.
- **024 (rejected):** the full-screen window isn't the cause, and nothing tried brings desktop duplication close to WGC: its first real frame still takes about 6 s.
- **025 (partly rejected):** detecting the prompt through KVP works (about 3 s, about 100 ms per read), but the Hyper-V console can't see a GPU-P VM's display, so it can't answer it.
- **026 (adopted):** the helper reads the prompt and answers it; end to end the host lists it 1.1–1.2 s after it opens and an answer takes about 5 s. An answer for a prompt that changed is refused. See [Administrator prompts](/gpuvm/docs/architecture/#administrator-prompts).
