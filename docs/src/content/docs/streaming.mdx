The Hyper-V console only shows the basic Hyper-V display, not what the GPU draws. To see the VM with the GPU, GpuVM installs a streaming server inside the VM and shows it in its own viewer, inside the app.

## Components

| Component | Where | Role | Pinned version |
|---|---|---|---|
| [Sunshine](https://github.com/LizardByte/Sunshine) | VM | Captures the virtual display and encodes with NVENC. | `v2026.914.233613` |
| [Virtual Display Driver](https://github.com/VirtualDrivers/Virtual-Display-Driver) | VM | A monitor drawn by the GPU. | `25.7.23` |
| [nefcon](https://github.com/nefarius/nefcon) | VM | Command-line driver installer; creates the virtual display device. | `v1.14.0` |
| [usbip-win2](https://github.com/vadimgrn/usbip-win2) | VM | Plugs in GpuVM's USB speaker, which Sunshine captures. | `0.9.8.0` |
| [ViGEmBus](https://github.com/nefarius/ViGEmBus) | VM | Virtual gamepad bus: Sunshine creates on it the controllers the viewer forwards. | `v1.22.0` |
| [GpuVM viewer](#gpuvm-viewer) | Host | Shows the VM inside the app. Built on Moonlight. | Bundled with GpuVM |
| [Moonlight](https://moonlight-stream.org) | Host | Shows the VM when it is opened from the CLI. | Installed separately |

The installers are downloaded on the **host** when the VM is created, verified against the SHA-256 pinned in `streaming/components.json` and copied to the VM's disk. The guest downloads nothing. They are kept in a `cache` folder (in `%ProgramData%\GpuVM` when installed).

nefcon is pinned to v1.14.0, the version the official VDD install script uses, even though v1.21.0 exists. ViGEmBus 1.22.0 is its last release (the project is archived); it is installed the first time a VM opens.

## Sunshine

Sunshine runs inside the VM. Its username and password are generated when the VM is created; on the host they are stored encrypted with DPAPI. The password travels in plain text to the guest only for the install and is deleted afterwards.

Each time you **start and open** a VM, GpuVM reads Sunshine's display list through its API, sets `output_name` to the virtual display and restarts Sunshine if that changed, so it never captures the Hyper-V display by mistake. When GpuVM has already turned the Hyper-V display off, it also sets `dd_configuration_option` to `disabled`: if Sunshine changes the display on every session, it re-tests all its encoders and the first frame takes 22 to 27 s instead of about 2 s ([lab 008](/docs/labs/#what-the-labs-found-so-far)). Changing the resolution or FPS still costs 10 to 15 s, because Sunshine sees the display change; GpuVM sets the display before the rest of the work and restarts Sunshine right away, so that time overlaps with it. Otherwise it uses `ensure_only_display`.

On NVIDIA GPUs, GpuVM also sets `nvenc_twopass` to `disabled`: NVENC encodes each frame in a single pass, about 1 ms less per frame. The mean input latency goes from about 13.4 to 11.4 ms. Machines created earlier get it the next time they are opened.

Work inside the VM that lasts until Windows restarts (display mode, capture mode, audio) is done once per boot, through one PowerShell Direct session, and Windows readiness is read from Hyper-V's heartbeat. Opening a VM that is already on takes about 7 to 10 s until the first frame; from off, about 55 s to the picture, mostly Windows booting and Sunshine starting (it tests its encoders before its API answers). In the app, **Open** waits for the viewer's first picture. From the CLI, `connect` returns only when Moonlight shows the first frame, and when the VM is already open in Moonlight it brings that window to the front instead of opening another.

## Capture modes

Every machine runs **GpuVM's own Sunshine** ([gpuvm-sunshine](https://github.com/alenj0x1/gpuvm-sunshine): upstream Sunshine at the version GpuVM pins, plus a Windows.Graphics.Capture helper adapted from Vibeshine), always as a Windows service (SYSTEM), whatever the machine is used for. It goes over the official install when a machine is created, and machines made before it get it the next time they are opened. Only administrators read its settings and keys.

It can capture the virtual display in two ways, chosen per machine in **Picture and control → Capture** or with `Set-GpuVMCapture -Name <vm> -Mode wgc|ddx`:

| Mode | In the app | Shows | Doesn't show |
|---|---|---|---|
| `wgc` (Windows.Graphics.Capture) | **Fast** (the default) | The picture a few seconds after connecting, and programs in exclusive fullscreen at any resolution. A small helper (`tools\sunshine_wgc_capture.exe`) captures in the signed-in user's session with that user's own rights and hands the frames to the service through a shared GPU texture; it holds nothing secret. | Windows' administrator prompts (they are drawn on the secure desktop); GpuVM [shows and answers them](#administrator-prompts). |
| `ddx` (desktop duplication) | **Classic** | Windows' administrator prompts too. | On the virtual display over GPU partitioning, desktop duplication loses access after every frame (lab 055): the picture can stay black. Programs in exclusive fullscreen: black. |

The mode is applied right away if the VM is running and checked on every **Start and open**; when it's already set, Sunshine isn't restarted. Applying it needs the guest password. VMs that never chose a mode use `wgc`. Machines from before GpuVM's Sunshine ran it in the user's session from a logon task; the first open removes that task.

## Administrator prompts

With `wgc`, Windows' administrator prompts (UAC) can't be streamed, and the Hyper-V console can't show them either: it doesn't see the GPU display. GpuVM brings them to the host instead:

1. **Watcher in the VM.** On the first open, GpuVM installs `guest/admin-prompt.ps1` in `C:\Program Files\GpuVM\AdminPrompt` (only administrators can change it) as the `GpuVM-AdminPrompt` task, which runs as SYSTEM from boot. When a prompt opens, it reads the program and publisher and publishes them through Hyper-V's data exchange (KVP); when it closes, it publishes that too.
2. **Card on the host.** The app reads that data every 2 s (`Get-GpuVMAdminPrompt`, about 100 ms, no PowerShell Direct) and shows an always-on-top card with the program, the publisher, **Allow** and **Deny**. A prompt shows on the host about a second after it opens.
3. **Answer.** `Resolve-GpuVMAdminPrompt` goes through PowerShell Direct with the guest password; the script starts a one-time helper as SYSTEM on the secure desktop of the console session, which presses Yes or No with UI Automation, only if the prompt open is still the one shown. An answer takes about 5 s.

Only the host can order an answer: nothing in the VM can approve a prompt for itself, and a prompt that changed in the meantime is never answered.

## Virtual display

The [Virtual Display Driver](https://github.com/VirtualDrivers/Virtual-Display-Driver) adds a monitor drawn by the GPU. It is installed with nefcon, and only the certificate that signed the driver is trusted.

- After the first boot the VM restarts once on its own to leave the virtual display as its only display.
- If the virtual display works, the Hyper-V display is turned off so Windows and Sunshine use the virtual one (`disableHyperVVideo` in the profile).
- On every **Start and open**, with the guest password saved, the virtual display is kept as the only and primary display of the VM. GPU-P VMs get an extra hidden 1024×768 output of the shared GPU; if it became the primary one, new windows (Steam, installers) would open where the stream doesn't show them. When it's already set, nothing is changed, so Sunshine doesn't re-test its encoders.
- If something fails, the VM is still reachable over Remote Desktop.

<Aside type="caution">
Don't use Remote Desktop while streaming: it takes the console session away. GpuVM moves the session back to the GPU display on the next **start and open** if it has the guest password.
</Aside>

## GpuVM viewer

The app shows each machine in GpuVM's own viewer, built on [Moonlight](https://github.com/moonlight-stream/moonlight-qt). The fork lives in a separate repository, [`gpuvm-viewer`](https://github.com/alenj0x1/gpuvm-viewer) (branch `gpuvm`), under GPL-3.0, and the installer bundles it. It only streams: what goes around the picture (the waiting screen, the side panel, the administrator prompt card) is drawn by the app.

- **Opening.** While the machine connects, its cube moves to the center with the steps. Then the picture fills the window under the title bar.
- **Full screen.** A machine set to full screen goes full screen when its picture is ready. Full screen can also be toggled from the side panel.
- **Home.** **Home** in the title bar, in the side panel, or **Ctrl+Alt+Shift+H** zooms out to Home and keeps the machine connected. Opening it again goes straight back to its picture. **Settings → Window → Going back to Home from a machine → Disconnect it** disconnects it instead.
- **Switching machines** zooms out of one and brings the other to the center. One machine opens at a time.
- **The GPU goes to the machines.** The app's holograms and scenes stop while a machine's picture is shown, inside the app or full screen, and draw at 30 FPS while GpuVM doesn't have the focus. **Settings → Appearance** can limit them further ([Settings](/docs/using-the-app/#settings)).

The viewer runs isolated, without administrator rights, because it reads what a server inside the VM sends. See [Architecture](/docs/architecture/#the-viewer).

### Side panel

**Ctrl+Alt+Shift+G** opens a panel beside the picture and pushes the picture aside. It is a board of widgets:

- machines with their cubes, to switch to another one;
- actions: **Home**, **Full screen**, **Stats on the picture** and **Disconnect**;
- the picture's numbers with their history;
- a clock, a shelf with every machine's figures, the games and the weather.

**Edit** adds, removes, moves and resizes widgets; **Done** ends it. The layout is remembered, and each widget shows more as it grows. Drag the panel's left edge to make it wider. The weather stays off until you type a city: only the city's name goes to [Open-Meteo](https://open-meteo.com), then its coordinates for the forecast. No account or key is needed.

### Pairing and picture settings

Pairing is automatic: the viewer generates the PIN and GpuVM hands it to Sunshine through its API. The viewer pairs as this PC's name followed by `GpuVM`, apart from a Moonlight paired from the same PC.

- To pair again: **Pair Moonlight again** in the machine's **⋯** menu, or `./gpuvm.ps1 connect -Name <vm> -Pair`.
- The resolution, frame rate, V-Sync, frame pacing, mouse, codec and bitrate are set in the machine's **Picture and control** section (or with `Set-GpuVMStreamingClient`), or per connection:

```powershell
./gpuvm.ps1 connect -Name win11 -Resolution 2560x1440 -Fps 120 -BitrateKbps 40000 -Codec HEVC
```

Codecs: `auto`, `H.264`, `HEVC`, `AV1`. The viewer opens the `Desktop` app of Sunshine by default.

### From the CLI

`./gpuvm.ps1 connect` (`Connect-GpuVM`) opens the machine in Moonlight installed on the host, under Program Files ([Install](/docs/install/#install-moonlight)). `Connect-GpuVM -Viewer` gets the machine ready and pairs GpuVM's viewer, then returns the stream arguments (`viewerLaunch`) without opening anything: the app uses it and starts the viewer itself.

### Frame rate, V-Sync and latency

An FPS of `0` (**Monitor** in the app) means the refresh rate of the host monitor the machine opens on, read every time the VM opens. When the VM's virtual display lacks that rate, GpuVM adds it to the display's modes, so the VM draws exactly one frame per monitor refresh. At the monitor's own rate V-Sync adds no latency, so the picture never tears without giving anything up, and stutters halve compared with a rate that doesn't match the monitor.

From a key, click, mouse move or gamepad button on the host to the change in the picture takes about 16.6 ms (median) at 120 FPS or more; the same PC without streaming takes 5.6 ms, so the stream adds about 11 ms. At 60 FPS it adds one more host frame. Codec and window mode don't change the median. Frame pacing gives the most even motion at 60 FPS; at 120 FPS and above it adds stutters, so only the **Movies and video** use turns it on.

## Gamepads

The viewer forwards the controllers connected to the host, and Sunshine creates them inside the VM on [ViGEmBus](https://github.com/nefarius/ViGEmBus), so Windows in the VM sees an Xbox 360 controller. GpuVM downloads the driver on the host, checks its SHA-256, copies it into the VM and installs it the first time the VM opens; Sunshine restarts to see it. A button press reaches the picture in about 17 ms.

## Audio

Hyper-V Generation 2 VMs have no sound card. GpuVM gives the VM **its own USB speaker**: a small server inside the VM (`GpuVMAudio.exe`) presents itself as a USB audio device (48 kHz, stereo), [usbip-win2](https://github.com/vadimgrn/usbip-win2) plugs it in, and Windows drives it with its built-in USB audio driver as if it were real hardware. It shows up as **Speakers (GpuVM Audio)** and Sunshine captures it (`virtual_sink`).

- Nothing leaves the VM: the server listens on `127.0.0.1` only, runs as `LOCAL SERVICE` and its program lives in `C:\Program Files\GpuVM\Audio`, where only administrators can write.
- usbip-win2 installs only its client, silently. Its drivers are signed by Microsoft: no test mode, no certificate of its own. GpuVM checks both and uninstalls it if either fails.
- The speaker is persistent: usbip-win2 plugs it in again every time Windows starts, so no restart or sign-in is needed. **Start and open** checks it in the background on the first open after each boot, plugs it in again if it was lost and updates the server when GpuVM brings a new one.
- VMs created with VB-CABLE move to the speaker the next time they are opened. VB-CABLE's output is silent to Sunshine inside a VM, so the earlier sound came from Steam Streaming Speakers ([labs 011 and 012](/docs/labs/)).

## Profile settings

The `streaming` section of the [profile](/docs/profiles/) sets the defaults:

```jsonc
"streaming": {
  "provider": "sunshine",            // or "none" to create the VM without streaming
  "virtualDisplay": true,
  "disableHyperVVideo": true,
  "audio": "usb",                    // or "none" to skip audio
  "sunshine": { },                   // extra keys for sunshine.conf
  "client": { "app": "Desktop", "resolution": "1920x1080", "fps": 0, "vsync": true, "framePacing": false, "mouse": "capture", "bitrateKbps": 0, "codec": "auto" }
}
```

`fps` is 10–480, or `0` for the host monitor's refresh rate. `vsync` and `framePacing` (true/false) are passed to the viewer; frame pacing is turned off whenever V-Sync is off, because the viewer only paces frames with V-Sync. `mouse` is `capture` (the VM takes the mouse, for games) or `absolute` (the pointer moves freely, as in remote desktop). `client` also accepts `performanceOverlay` (true/false) and `displayMode` (`fullscreen`, `windowed`, `borderless`), only passed to the viewer when the profile defines them. `captureSystemKeys` (`never`, `fullscreen`, `always`; `fullscreen` if not set) decides when Alt+F4, Alt+Tab and the Windows key go to the VM; Ctrl+Alt+Shift+Q always quits the stream.

The viewer, and Moonlight from the CLI, run as the signed-in user without administrator rights, even though the GpuVM service runs elevated: they talk to a server the VM controls.

## Updating components

```powershell
./gpuvm.ps1 components-update -WhatIf   # see whether newer versions exist
```

It looks up the latest GitHub release of each component and updates version, URL and SHA-256 in `streaming/components.json`. usbip-win2 stays on 0.9.8.0 and ViGEmBus on its last release, 1.22.0 (`hold` in the file). A new version isn't tested: validate it in a [lab](/docs/labs/) before creating VMs with it. The app can't run this command.
